# Guía del generador del registro de módulos

Esta guía explica qué hace el subcomando `generate-module-registry` del CLI, cuándo se ejecuta, quién lo usa y qué archivo modifica.

## Respuesta corta

El generador lee los módulos dentro de `addons/` y actualiza estos archivos Go:

```text
internal/modules/backend/factories_gen.go
internal/modules/assets/static_assets_gen.go
addons/<modulo>/static_assets_gen.go
```

El registro de módulos, el registro compartido de assets y los archivos `static_assets_gen.go` de cada addon son código generado, quedan dentro del repositorio y Go los compila dentro de la aplicación. El generador no guarda registros en MongoDB.

## Quién lo usa y cuándo

Lo usa quien desarrolla o mantiene módulos backend:

- Al crear un módulo nuevo.
- Al eliminar un módulo.
- Al cambiar qué paquetes de módulo deben compilarse en el backend.

No hace falta ejecutarlo al iniciar la API ni después de cada cambio interno de un módulo. `make run`, `go build` y `go test` no invocan `go generate` automáticamente.

Si creas el esqueleto con el CLI del repositorio, el generador se ejecuta al final de ese comando:

```powershell
go run ./cmd/goep create-module invoices
```

Si creas o eliminas el módulo manualmente, ejecútalo desde la raíz del repositorio:

```powershell
go generate ./internal/modules/backend
```

Ese comando encuentra la directiva `//go:generate` de `internal/modules/backend/factories.go`. La directiva ejecuta el subcomando `generate-module-registry` del CLI con `addons/` como entrada. Genera `factories_gen.go`, un `static_assets_gen.go` dentro de cada addon con `static/`, y `internal/modules/assets/static_assets_gen.go`, que los agrupa para producción.

También puedes ejecutar el programa directamente desde la raíz. Sus valores por defecto usan las mismas rutas:

```powershell
go run ./cmd/goep generate-module-registry
```

En el trabajo normal, usa el CLI para crear módulos y `go generate` para regenerar después de cambios manuales. No edites `factories_gen.go` directamente.

## Qué archivos lee

El generador recorre cada subdirectorio directo de `addons/`. Para cada módulo backend (manifiesto sin `type` o con `"type": "backend"`) requiere un constructor y `RegisterBackendModule`. Para cada módulo con `"type": "web"` requiere `RegisterWebModule(*modules.Registry) error`. Ambos tipos se enlazan en `NewCompiledRegistry`; el compositor inicializa primero los módulos backend y después los módulos web con los servicios disponibles.

1. `manifest.json` con un campo `name` no vacío.
2. Un paquete `config/` con exactamente un constructor exportado cuya forma sea `func Nombre(ModuleConfig) (*Module, error)`.
3. Para módulos backend, una función `RegisterBackendModule`; para módulos web, una función `RegisterWebModule`. Debe estar declarada en algún archivo Go de `config/`.

Por ejemplo, para `addons/invoices/`, espera una estructura similar a esta:

```text
addons/invoices/
├── manifest.json
└── config/
    ├── module_config.go
    └── backend_module.go
```

El generador no inspecciona ni genera código para `domain/`, `service/`, `handler/` o `repository/`. Esos paquetes contienen la implementación del módulo y quedan fuera de la lista de registro.

## Qué código genera

`factories_gen.go` importa el paquete `config` de cada módulo y crea `NewCompiledRegistry()`. Esa función crea un registro en memoria y llama a `RegisterBackendModule` para módulos backend y `RegisterWebModule` para módulos web.

Para assets, genera `addons/<modulo>/static_assets_gen.go` junto al código del módulo. Cada archivo embebe solo `static/dist/`. Luego `internal/modules/assets/static_assets_gen.go` crea un mapa que relaciona el nombre del manifiesto con el filesystem embebido del addon. Este paquete separado evita que el servicio estático dependa del paquete de composición backend. En forma simplificada:

```go
// addons/invoices/static_assets_gen.go
package module

import "embed"

//go:embed static/dist
var StaticAssets embed.FS

// internal/modules/assets/static_assets_gen.go
package assets

var StaticDirectories = map[string]fs.FS{
    "invoices": assetModuleN.StaticAssets,
}
```

El compilador de assets crea `static/dist/module-assets.json` incluso cuando el módulo no declara scripts, estilos o archivos públicos. Ese marcador permite que Go compile el `embed`; el servidor no lo publica como un asset.

El registro de fábricas tiene esta forma simplificada:

```go
// Code generated by goep generate-module-registry; DO NOT EDIT.
package backend

import (
    module0 "github.com/GoEnterpricePlatform/goEP-core/addons/ai-tool-calling/config"
    module1 "github.com/GoEnterpricePlatform/goEP-core/addons/billing/config"
    // ...un import por cada módulo...
    "github.com/GoEnterpricePlatform/goEP-core/internal/modules"
)

func NewCompiledRegistry() (*modules.Registry, error) {
    registry := modules.NewRegistry()
    if err := module0.RegisterBackendModule(registry); err != nil {
        return nil, err
    }
    if err := module1.RegisterBackendModule(registry); err != nil {
        return nil, err
    }
    // ...una llamada al registrador correspondiente por módulo...
    return registry, nil
}
```

Los alias `module0`, `module1`, etc. son nombres que genera el programa para los imports. Los módulos se ordenan por el nombre de su manifiesto, así que el número no es un identificador permanente del módulo.

## Ejemplo: agregar `invoices`

Después de crear el manifiesto y el paquete `config` de Invoices, ejecuta:

```powershell
go generate ./internal/modules/backend
```

El generador revisa también los demás directorios de `addons/`, ordena los módulos y actualiza `internal/modules/backend/factories_gen.go`. En este ejemplo, `moduleN` representa el alias numérico que el generador asigna a ese paquete:

```go
moduleN "github.com/GoEnterpricePlatform/goEP-core/addons/invoices/config"
```

y registrará el adaptador:

```go
if err := moduleN.RegisterBackendModule(registry); err != nil {
    return nil, err
}
```

En el archivo real el alias sería `module0`, `module1` y así sucesivamente. Para `invoices`, el número depende de los nombres de todos los módulos presentes y de su orden alfabético. No lo elijas ni lo cambies a mano.

Después de regenerar, ejecuta la app normalmente:

```powershell
make run
```

La compilación incluye `factories_gen.go`. Al arrancar, el backend llama a `NewCompiledRegistry()` para registrar las implementaciones en memoria y compara ese registro con los manifiestos descubiertos en `addons/`. Después recorre los módulos en orden de dependencias; el estado de ciclo de vida determina si cada uno recibe el mux público o uno aislado para sus rutas API.

## Relación con MongoDB

El generador **no se conecta a MongoDB y no escribe datos**. Solo lee archivos y genera `factories_gen.go` en el repositorio.

La aplicación sí usa MongoDB durante el arranque para consultar y guardar el estado de ciclo de vida de los módulos (por ejemplo, si están instalados o habilitados). Ese proceso está separado de la generación del registro. Generar el archivo no instala ni habilita un módulo en la base de datos.

## Si olvidas regenerar

- **Agregaste un módulo y ejecutas `make run` sin generar:** el descubrimiento encontrará su manifiesto, pero el registro compilado no tendrá su implementación. El backend informará que el módulo descubierto no tiene implementación compilada.
- **Eliminaste el paquete del módulo y no regeneraste:** `factories_gen.go` puede seguir importando el paquete eliminado y la compilación fallará.
- **Eliminaste solo el manifiesto y no regeneraste:** el registro puede contener una fábrica que ya no tiene manifiesto, y la validación del arranque fallará.
- **Cambiaste lógica dentro de un módulo existente:** no necesitas regenerar mientras sigan iguales la lista de módulos, el manifiesto y su registrador (`RegisterBackendModule` o `RegisterWebModule`).

## Errores que puede reportar

La generación se detiene si no puede leer un manifiesto, falta `name`, un módulo backend no tiene exactamente un constructor con la forma esperada o falta el registrador correspondiente al tipo. Corrige el módulo señalado y vuelve a ejecutar `go generate ./internal/modules/backend`.

Los archivos generados deben incluirse en el cambio junto con los archivos del módulo. Así, quien compile el repositorio obtiene los mismos registros sin ejecutar el generador al arrancar la aplicación.
